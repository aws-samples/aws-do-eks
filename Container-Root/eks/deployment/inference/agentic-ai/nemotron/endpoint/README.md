# Nemotron endpoint: a key-gated public URL for a Nemotron frontend, and a private API that hands out the key

The serving folders ([`../super`](../super), [`../ultra`](../ultra)) leave the Dynamo frontend as a ClusterIP Service
reachable only by port-forward, and the frontend has no request authentication of its own (`python3 -m dynamo.frontend
--help` on dynamo 1.5.0 lists TLS flags only). This folder adds the piece needed to let a group of people - for example
the attendees of a workshop running in other AWS accounts - use the model over the internet with an OpenAI-compatible
client, without exposing the frontend to everyone:

```
attendee (anywhere)  --TLS 443-->  cluster ingress controller (ingress-nginx, existing)
   --> Ingress ${GATEWAY_NAME}  host ${ENDPOINT_HOST}  certificate from cert-manager (ACME HTTP-01)
   --> Service ${GATEWAY_NAME}:8080 --> Deployment ${GATEWAY_NAME} (official unprivileged nginx, 2 replicas)
         403 unless  Authorization: Bearer <MODEL_KEY>      (MODEL_KEY from Secret ${GATEWAY_SECRET_NAME})
   --> http://${TARGET_SERVICE}.${NAMESPACE}.svc.cluster.local:8000   (the frontend, unchanged; the header is stripped)

workshop / consumer account (VPC with an execute-api endpoint)  --SigV4 POST /modelkey-->  PRIVATE REST API (us-west-2)
   --> Lambda --> Secrets Manager secret {"endpoint", "model", "api_key"}  --> 200 to the caller, 404 when retired
```

| Folder | What | Deploy / remove |
|---|---|---|
| [`gateway/`](gateway) | the key gate: `keygate.yaml-template` (ConfigMap + Deployment + Service + Ingress) rendered by `envsubst` from `.env`, `secret-sync.sh` (copies the key from Secrets Manager into the cluster Secret, through a pipe), `dns-cname.sh` (the CNAME to the ingress load balancer), `test.sh` | `./run.sh` / `./stop.sh` |
| [`modelkey-api/`](modelkey-api) | one CloudFormation template: Secrets Manager secret (the key is **generated in the account**, it never exists in a file), Lambda + least-privilege role, PRIVATE RestApi with `POST /modelkey` (`AWS_IAM`) + resource policy, deployment + stage; `rotate.sh`; offline tests | `./deploy.sh` / `./remove.sh` |
| [`consumer/`](consumer) | documentation + snippets for the calling side: the execute-api VPC endpoint, the `execute-api:Invoke` statement, the SigV4 call, storing the key as SSM parameters, attendee curl / openai SDK / Strands snippets | nothing to deploy |

Why one CloudFormation template rather than a CDK app: this repository is `.env` + `envsubst` templates + bash + the
AWS CLI throughout and carries no CDK application; a single template with an inline Lambda needs no toolchain, no
bootstrap and no asset bucket, and deploys and removes with one command each like every other folder here.

## Prerequisites

- A Nemotron deployment from `../super` or `../ultra` (any `MANIFEST_TYPE` that creates the `${DEPLOYMENT_NAME}-frontend`
  Service), in namespace `NAMESPACE`.
- On the cluster: an ingress-nginx controller with a public load balancer (`INGRESS_CLASS`, default `nginx`) and
  cert-manager with an ACME `ClusterIssuer` (`CLUSTER_ISSUER`, default `letsencrypt-prod`). The gateway uses standard
  Ingress annotations only, so a controller with snippet annotations disabled is fine.
- A public DNS name you control (`ENDPOINT_HOST`) - `dns-cname.sh` creates the record when the zone is in Route 53.
- AWS rights for the API stack (CloudFormation, IAM, Lambda, API Gateway, Secrets Manager) in `API_REGION`.

## Deploy, in this order

```bash
cd /eks/deployment/inference/agentic-ai/nemotron/endpoint

# 1. the key and the private API (us-west-2 by default; generates the key in Secrets Manager)
cd modelkey-api && ./config.sh && ./deploy.sh && cd ..

# 2. the key into the cluster (Secrets Manager -> Kubernetes Secret, through a pipe; also the rotation step)
cd gateway && ./config.sh && ./secret-sync.sh

# 3. the DNS name BEFORE the Ingress (the ACME HTTP-01 challenge is answered through it)
HOSTED_ZONE_ID=Z... ./dns-cname.sh          # or create the CNAME to the ingress load balancer by hand

# 4. the gateway + Ingress; the certificate follows 1-3 minutes after the name resolves
./run.sh
kubectl -n <namespace> get certificate       # READY=True
./test.sh                                     # no key -> 403; key -> 200 + model list; streamed completion
```

Then hand the consumer side (`consumer/README.md`) the `ApiId` / `InvokeUrl` / `InvokeArn` outputs of step 1.

Rotation: `modelkey-api/rotate.sh` (new value generated by Secrets Manager) then `gateway/secret-sync.sh` (the gateway
restarts on the new key; every copy of the old key stops working). Retire: `gateway/stop.sh` deletes the gateway, the
Ingress and the key Secret (the TLS certificate Secret is kept unless `DELETE_TLS=1`, to stay clear of ACME duplicate
limits); `modelkey-api/remove.sh` deletes the API, the Lambda and the secret.

## Knobs

All `${VAR:-default}`; a launch-line override wins (`NAMESPACE=myns ENDPOINT_HOST=nemotron.example.org ./run.sh`).

| Where | Knob | Default | Meaning |
|---|---|---|---|
| gateway | `NAMESPACE`, `DEPLOYMENT_NAME` | `default`, `nemotron35-super-vl-120b-agg` | where the frontend is; `TARGET_SERVICE` = `${DEPLOYMENT_NAME}-frontend`, `TARGET_PORT` 8000 |
| gateway | `GATEWAY_NAME`, `GATEWAY_IMAGE`, `GATEWAY_REPLICAS` | `nemotron-keygate`, `public.ecr.aws/nginx/nginx-unprivileged:1.28-alpine`, 2 | the key gate; pin a digest for a frozen deployment |
| gateway | `RATE_LIMIT_RPS`, `PROXY_TIMEOUT`, `MAX_BODY_SIZE` | 20, 600, 20m | per-source-IP rate limit, upstream timeouts (s), request body (images) |
| gateway | `ENDPOINT_HOST`, `HOSTED_ZONE_ID`, `CLUSTER_ISSUER`, `INGRESS_CLASS` | `nemotron.example.com`, -, `letsencrypt-prod`, `nginx` | the public name and how it gets its certificate |
| gateway | `SECRET_REGION`, `SECRET_NAME`, `GATEWAY_SECRET_NAME` | `us-west-2`, `nemotron/modelkey`, `${GATEWAY_NAME}` | where secret-sync.sh reads the key and the cluster Secret it writes |
| modelkey-api | `API_REGION`, `STACK_NAME`, `STAGE_NAME`, `SECRET_NAME` | `us-west-2`, `nemotron-modelkey-api`, `dev`, `nemotron/modelkey` | the stack |
| modelkey-api | `ENDPOINT_URL`, `MODEL_ID` | `https://${ENDPOINT_HOST}/v1`, `nvidia/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B-BF16` | returned to callers beside the key |
| modelkey-api | `PRINCIPAL_ORG_ID`, `SOURCE_VPCE_IDS` | empty | optional pins of the resource policy: one AWS Organization, specific VPC endpoints |

## What it is, and is not

- The frontend stays a ClusterIP Service; nothing in the serving folders changes. The gateway strips the
  `Authorization` header, so the key never reaches the frontend or its logs.
- The key is a **shared secret for one event**: everyone who holds it is the same user to the model. Per-user keys,
  budgets or request logs need a key-aware proxy (for example LiteLLM) in place of the key gate.
- "Only callers inside approved accounts": the key is delivered only to AWS identities allowed `execute-api:Invoke` on
  the method that reach the private API through an execute-api endpoint in its region. Unpinned, that is "any AWS
  account that knows the API id and has an endpoint"; `PRINCIPAL_ORG_ID` and `SOURCE_VPCE_IDS` narrow it. The public
  URL itself is on the internet (its certificate appears in certificate-transparency logs within minutes); without the
  key every request gets 403 from the gateway and never touches the frontend.
- Streaming works end to end (`proxy_buffering off` on the gateway and the Ingress). A non-streamed answer is one
  write at the end; a shared load balancer in front of the controller may close an idle connection at 60 s, so tell
  clients to stream or keep `max_tokens` <= 512 (a 512-token answer takes ~45 s on one H200 node).
